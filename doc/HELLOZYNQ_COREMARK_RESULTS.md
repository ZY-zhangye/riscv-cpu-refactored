# HelloZynq RV32 SoC：160 MHz 参数与性能说明

日期：2026-10-18，Asia/Singapore。本文依据已经完成的实板日志和 Vivado Routed 报告整理；没有为本次汇报改变硬件或重新跑分。

**160 MHz 实板 CoreMark 为 343.752372，约 2.148452 CoreMark/MHz，三项 CRC 正确，两次运行复现。但该实现静态时序未收敛：WNS 为 −2.449 ns。** 这是本轮最高通过 CoreMark 的超频实验点，不能视为已保证跨电压、温度和器件差异稳定工作的频率。本轮 10 MHz 步进中，最高同时满足所设时序约束且通过 CoreMark 的点是 **100 MHz**。

| 项目 | 结果 |
| --- | ---: |

| CoreMark 吞吐 | **343.752372 次/秒** |
| 归一化成绩 | **2.148452 次/秒/MHz** |
| 最终计时迭代数 | 6,000 |
| 有效计时 | **17.454425 秒** |
| CPU 周期数（Timer 换算） | **2,792,708,000** |
| 每次迭代平均周期数 | 465,451.333 |
| cycle CSR 差值 | 2,792,707,994，与 Timer 换算差 6 周期 |
| seed / list / matrix / state CRC | e9f5 / e714 / 1fd7 / 8e3a |
| 最终累计 CRC | a14c（与迭代数相关） |
| 固件 build ID | 75c7f53c0397 |

使用原 CoreMark 算法和校验框架，静态分配总计 2,000 字节工作区，三算法各分得 666 字节，单核单上下文。`--iterations 0` 表示先自动校准，最终确定 6,000 次；日志中的 `timing_runs=4` 包含校准过程，成绩只取最后一次计时。

计时 Timer 每 160 个 CPU 周期递减一次：`17,454,425 ticks × 160 = 2,792,708,000 cycles`。按配置的 CPU 频率独立复算：

```text
CoreMark = 6000 × 160000000 / 2792708000 = 343.752372249...
CoreMark/MHz = 343.752372249... / 160 = 2.148452326...
测时秒数 = 2792708000 / 160000000 = 17.454425
```

原框架因 `HAS_FLOAT=0`，先将秒数截断成 17，再显示整数 `Iterations/Sec: 352`；**352 不是准确分数**。本文采用移植层基于原始 ticks 和配置频率计算的精确成绩，主机另行复算。官方框架同时打印 `Correct operation validated.`，满足 CRC 和至少 10 秒条件；这是一份本地板级测量，不是 EEMBC 认证或登记成绩。

首次 160 MHz 采集与恢复该配置后的最终采集均通过，原始 UART 字节完全相同，长度各 1,477 字节。最终采集进程的 71.58 秒包含等待 JTAG 下载、校准和输出，不能代替用于计分的 17.454425 秒。

## 时序余量与具体限制

工具为 Vivado 2023.2，报告状态 Routed，采用配套教程候选器件 `xc7z020clg484-2`。实物速度档、温度等级和 PCB 版本仍未确认；频率来自板载 50 MHz 时钟及 MMCM 配置，未用仪器独立校准晶振。

| 时序项目 | 160 MHz 报告结果 |
| --- | ---: |
| 最差建立余量 WNS | **−2.449 ns** |
| 总负建立/恢复余量 TNS | −6,463.526 ns |
| 失败端点 / 总端点 | 6,182 / 18,796 |
| 最差保持余量 WHS | **+0.062 ns** |
| 总负保持余量 THS / 失败端点 | 0 ns / 0 |
| 最差脉宽余量 WPWS | +1.995 ns |
| 总负脉宽余量 TPWS / 失败端点 | 0 ns / 0 |
| 未约束内部端点 / 无时钟寄存器 | 0 / 0 |

6,182 个失败端点包括两组：CPU 同钟 setup 的 5,511 个端点（TNS −6,231.245 ns），以及复位 recovery 的 671 个端点（TNS −232.281 ns，最差 −1.311 ns）。因此，**建立/恢复时序失败；保持时序没有失败**。

最差建立路径在 EX 阶段，从 `ds_to_es_bus_r_reg[5]` 到 `skid_exe_result_reg[25]`。可用周期 6.250 ns，数据路径延迟 8.586 ns：逻辑 3.985 ns（46.410%），布线 4.601 ns（53.590%）；共 15 级逻辑，包括 9 个 CARRY4 和 6 个 LUT。时钟不确定度为 0.088 ns。当前瓶颈表现为执行结果路径的组合逻辑深度及布线延迟。

最差复位恢复路径为 `cpu_reset_n_reg` 到 Timer 的 `timer_load_reg[13]/CLR`，数据延迟 7.173 ns，其中布线 6.689 ns。后续若要做可靠的高频版本，板级复位分发和该执行结果路径都需要处理；本文仅说明现状，未修改本次已测实现。

CoreMark 通过与 STA 失败可以同时存在：板上这颗器件、当时环境和该程序的数据路径能够完成测试，并不等于所有路径在工具建模的最坏工艺、电压和温度条件下都满足要求。不能从本次通过推导任意程序长期稳定，也不能用一条路径的倒数直接宣称新的保证频率。

## 逻辑、存储器和时钟资源

以下为整个 `hellozynq_top` 的 Routed 资源，包含 CPU、现有外设、ROM/RAM 和板级壳，不是单独 CPU 核面积。

| 资源 | 使用 / 可用 | 占用率 |
| --- | ---: | ---: |
| LUT 总计 | 6,723 / 53,200 | **12.64%** |
| 其中 LUT 逻辑 | 6,487 / 53,200 | 12.19% |
| 其中 LUTRAM | 236 / 17,400 | 1.36% |
| FF | 5,368 / 106,400 | **5.05%** |
| Slice | 2,725 / 13,300 | 20.49% |
| BRAM36 | 68 / 140 | **48.57%** |
| DSP48 | 4 / 220 | **1.82%** |
| IOB | 6 / 200 | 3.00% |
| BUFG | 2 / 32 | 6.25% |
| MMCM | 1 / 4 | 25.00% |
| Latch / Black box | 0 / 0 | — |

LUTRAM 的可用数量是支持存储功能的 LUT 子集，不能把该百分比与 LUT 逻辑百分比直接相加。BRAM 的 68 块对应 16 KiB 指令存储器和 256 KiB 数据存储器，数据 RAM 64 块、指令 ROM 4 块；4 个 DSP 用于乘法部分积。资源容量仍有余量，提高频率需要缩短路径，单纯剩余 LUT 多不会自动改善时序。

时钟配置为输入 50 MHz，MMCM 输入除 1、反馈乘 16、输出除 5，VCO 800 MHz，得到 CPU 160 MHz；所有测试程序的时钟常量按该配置编译。UART 为 115200/8N1，BAUD 寄存器 1388、CTRL=0x14。SoC 使用片内 ROM/BRAM，没有接入 PS DDR；代码入口为 `0x80000000`，数据区为 `0x80100000`。

固件 `.text` 为 12,744 字节；`.rodata` 3,248 字节、`.data` 8 字节、BSS 2,084 字节，位于数据 RAM，另预留 8 KiB 栈。没有把 15,992 字节的 GNU size “text” 汇总误当成全部位于指令 ROM。

## DRC、CDC 与功耗报告的解释

`serious_drc_count=0` 只表示本脚本检查的 DRC Error/Critical Warning 为零，不能描述成所有检查全绿：

- DRC 报告仍列出 33 条 Warning：DSP 输入流水 8 条、DSP MREG 3 条、RAM 异步控制 20 条、规则计数上限提示 1 条、未实例化 PS7 提示 1 条。RAM 异步控制规则达到展示上限 20，实际相关路径不一定只有 20 条。
- CDC 报告为 CDC-7 Critical 12 条、CDC-2 Warning 1 条、CDC-9 Info 1 条。主要涉及复位异步清零端及 UART 同步链缺少 ASYNC_REG 属性，不能将 DRC 无严重项等同于 CDC 通过。
- Methodology 报告列出 LUTAR-1×1、SYNTH-15×64、TIMING-16×1000，共 1,065 条 Warning；建立时序问题已在上述负余量中体现。

Vivado 无活动文件的功耗估计为总片上功耗约 0.238 W，动态约 0.126 W、静态约 0.111 W，置信度 Medium。这是默认活动和环境假设下的工具估计，**不是实际 CoreMark 功耗、板卡输入功耗或温度测量**，不据此计算真实性能功耗比。

表中小数按显示位数截断，原始有理数和完整精度见 CSV/JSON。170 MHz 的 hold 余量也是正值（+0.050 ns）；失败不是已收到 CoreMark CRC 错误，而是该配置没有获得启动/完成证据。只据此确定本轮步进的最后通过 160 MHz、首次失败 170 MHz，未测 165 MHz，不能给出精确极限或特定 CPU 逻辑故障定位。

160 MHz 的吞吐约为 50 MHz 的 **3.200214 倍**，频率比为 3.2；每 MHz 的成绩仅相差约 **0.0067%**。提升基本来自频率，不能解释为 IPC 增加。各频率重新编译、迭代规模、计时开销及分支预测状态等可形成微小差别，本轮没有动态剖析数据来分配各因素比例。

这是单发顺序五级流水、片内固定延迟存储器上的整数工作负载。分支、访存相关和多周期乘法等会影响平均执行效率，但 **2.148452 CoreMark/MHz 不是 IPC**。没有可靠的动态退休指令统计，本工程 `INSTRET` 仍带分支/异常补偿，不能从本次日志计算 CPI 或 MIPS。

板级除法器采用真实 32 步迭代除法，保持现有 RV32M 接口。此次反汇编中，计时主体 `iterate/core_bench_list/core_bench_matrix/core_bench_state` 没有 DIV/REM 指令，相关除法主要出现在初始化、校准及打印计分中；因此不能把成绩主要归因于除法器慢。优化方向需要动态证据，不能凭剩余 DSP/LUT 数量推算性能增长。

编译器为 Windows 原生 xPack GCC 15.2.0，`-Os`、`rv32im_zicsr`、ILP32、medany，禁 small-data/relax，未生成 A/C/F/D 指令。`core_main.c`、list、matrix、state、util 五份框架/算法文件与仓库 HEAD 内容一致，修改集中在移植层。CPU 主流水源文件未改，SoC 调整主要为 RAM/ROM 和 bridge 返回时序，另添加板级壳与硬件除法实现。不同编译优化、存储系统或处理器上的 CoreMark 数值不能脱离配置直接比较。
